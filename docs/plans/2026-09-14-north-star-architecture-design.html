The vocabulary of the design. A term in code is also an identifier that appears in a file or a command.
TermMeans
operatorOne unit of physics: work and bytes as a function of dimensions and hardware rates. Named by its formula shape (§3). Never named after a model.
dimensionAn atomic tensor size an operator reads: hidden width, head width, KV width, FFN width, expert count, recurrent state.

runOne execution of one candidate with one seed. A leaderboard row usually aggregates several runs.

behaviour modelA learned statement of how a mechanism behaves: speculative acceptance by draft position, prefix hit rate, residency transitions. Not a kernel time.

extrapolationA result computed outside the scope of the numbers behind it. Reported as such rather than given a confidence (NS-5).

configuration leaderboardThe ranking of candidates for one scenario. Answers "what should we deploy?" Called the configuration board for short.

Called the calibration board for short. It is not scenario-specific: a pathway is scored on the whole set, and one of its rows is a configuration board scored against measured runs.
sweep driverThe part of blis rank that enumerates valid candidates, runs each seed, and aggregates rows.

translatorCode that reads one vendor's config dialect and emits layer groups. One per dialect.
value-preservingA release whose acceptance test is byte-identical output. It refactors without changing any number.
recalibrationA release that changes output by design, so byte-identity is a category error. A refit is part of the work.

§1Purpose

What BLIS is for

CurveBender needs BLIS to answer six questions. Each constrains the design.

The six use cases, from the CurveBender priorities deck. The right column is what each one requires from the architecture.
CaseQuestionRequires
1 OnboardWhat should we deploy? Rank the best few configurations when a new model arrives.Onboarding in tens of minutes, so no pull request in the path
2 ReplanWhat should we switch to? Keep the best alternatives current as traffic drifts.Re-ranking from observed evidence, continuously
3 Adaptive PDHow should prefill and decode split? Beat the llm-d defaults for this model and cluster.Policy behaviour that varies with model, cluster and workload
4 Policy discoveryWhich llm-d policies work best? Search the space before touching production.Policies as a searchable space, not hand-edited variants
5 Tune onlineHow should we tune now? Adjust routing weights against live traffic.A loop: observe, simulate, choose, apply
6 Infra co-designWhich storage and network knobs help? Let those teams evaluate ideas end to end.Fabric and storage as separately owned inputs

Cases 1 and 2 put onboarding cost on the critical path: a model that costs engineering time cannot be onboarded in tens of minutes, however good the physics. Cases 3, 4 and 5 need policies to be selectable and searchable rather than compiled-in choices. Case 6 needs the fabric to be an input a networking team can change without touching a model definition.

All six also need a confidence attached to each rank, because an engineer has to know when the answer is an extrapolation. That requirement drives §5 and the NS-5 invariant in §9.

§2Today

Where BLIS stands

Cited Day-zero runnability is good. GLM-5.2, GLM-5.3, Kimi-K3, Inkling and Nemotron-3.5-Lightning all run today with no code changes, using only standard command-line configuration. Discussion #1700 established this empirically.

Verified Fidelity costs pull requests. Onboarding Kimi-K3 took four, on top of a fifth that had established the latent-attention and model-shape groundwork for GLM-5.2. Two of the four changed only hardcoded Go literals: a config-key spelling, and an activation-function name.

Other measurements of the same pressure: forty-five of the last eighty commits touched CLAUDE.md, now 741 lines. The run command has 116 flags in a 3,275-line file. Step time is one 324-line function, and its physics is mirrored by hand in a second backend.

The two literal-only Kimi-K3 changes — what a config-key spelling costs today

Kimi-K3 declares its active-expert count as num_experts_per_token. BLIS read num_experts_per_tok. The expert count itself parsed fine, so the MoE consistency guard tripped and the run aborted before any simulation:

$ blis run --model moonshotai/Kimi-K3
fatal: NumLocalExperts > 1 requires NumExpertsPerTok > 0

The fix was to add the alias to a list in Go, then mirror it in a second parser to keep the two in sync. Separately, Kimi-K3 uses the SiTU-GLU activation; BLIS had a hardcoded allowlist of activation names, and an unrecognised name is a hard error from the KV-capacity calculation, so situ had to be added to that list too.

What the same two changes look like after R4a

  num_experts_per_tok:  [num_experts_per_token, n_active_experts]

Both were vocabulary gaps, not physics gaps. §3 explains why they became code changes, and R4a removes the category.

The one day-zero failure, and what it shows

Cited Nemotron-3-Ultra-550B aborts at startup. Its config does not carry a top-level layer count; the number of layers is the length of a block-type array. BLIS asks for the scalar field, reads zero, and panics. The 30B sibling has the same architecture, declares the field, and runs.

BLIS did not lack physics for that model. It asked the wrong question. num_hidden_layers has no answer in that config; what is the layer list? always has one, because every config describes its layers somehow. The design that follows takes layer groups as the primary description of a model.

§3Design

The refactor, in three levels

Three levels: dimensions, operators, and layer groups per model. What follows is what each level holds and why the boundaries fall where they do.

Step time is already a linear form

Verified Trained-physics step time computes nine named quantities, then combines them in a weighted sum with eleven coefficients. Seven of the nine are inline local variables in one function; two are already extracted as methods.

The nine terms of trained-physics step time as they exist on main. There are more coefficients than terms because prefill and decode each split into a compute and a bandwidth coefficient, while the three tensor-parallel collectives share one.
TermWhat it pricesStatus
tPfCompute, tPfKvPrefill compute and KV bandwidthinline
tDcCompute, tDcKvDecode compute and KV bandwidthinline
tWeightWeight loadinginline
tTpAttention, tTpDenseFFN, tMoEReduceThree tensor-parallel collectives, one shared coefficientvia tpAllReduceBasis
tMoEDispatchExpert dispatch and combinevia moeDispatchBasis
Four overhead termsPer layer, per request, per step, per MoE layerinline

So the refactor is not introducing a new abstraction. It is finishing one that is partly built. Most of the work is extraction, which can be checked against byte-identical output at each step.

That linear form is also a regression design matrix. Once the terms are addressable, a fitted coefficient becomes a named block with a validity domain, instead of a position in an array. That is the prerequisite for attaching confidence to a rank, which is what cases 1 and 2 need.

A model becomes layer groups over operators

Proposed Discussion #1700 adds the level above those terms. The design has three levels, and each is stable for a different reason.

Dimensions

Atomic tensor sizes: hidden width, head width, KV width, FFN width, expert count, recurrent state. Every model has them; only the values differ.

Operators

Work and bytes as a function of dimensions and hardware rates. Model-blind: never named after a model, never branching on architecture.

Model, as layer groups

How many layers run which operators, at which dimensions. The only per-model thing, and it is data.

Groups with counts, not a per-layer list

Verified The simulator consumes counts per layer type, never layer order. Every layer quantity in the step-time model is an integer count — MoE layers, dense layers, KV-bearing layers — and no code path indexes a layer or iterates in order. So the catalog should state counts directly rather than enumerate layers for the simulator to count back.

That is why the shape below is a short list of groups, each with a count, rather than one entry per layer. GLM-5.2 is two groups covering 78 layers; Kimi-K3 is two groups covering 93. A model whose FFN width varies layer by layer (Nemotron-NAS-style FFN widths) needs one group per distinct shape, which is still far shorter than one entry per layer.

The catalog is written for its consumer. Order is omitted because nothing reads it, and adding it would be a field that can drift from reality with no test able to catch it.

Today BLIS encodes layer wiring as flat scalar fields: a dense-prefix count, an interleave step, a KV-bearing-layer count. Each new wiring pattern therefore needs a new field, which is a code change. Layer groups express all of them, so the field-per-pattern category disappears.

Why this is the point of the refactor

Both models are now the same kind of object: a list of layer groups, each naming its operators and dimensions. first_k_dense_replace and full_attn_layers were two special-purpose fields for two wiring patterns. The list expresses both, and the next wiring pattern too, without a new field.

Layer groups are also the seam that makes both capacity and step time read the same description. §4 shows what happens when they do not.

The rule that separates an operator from a dimension

The rule is a test, so that it can be applied without a design review each time.

  • If the work-and-bytes formula shape differs, it is a new operator. Latent attention adds projection terms. Two linear-attention recurrences are different mathematics. A sparse-selection kernel is a new formula.
  • If only the numbers differ, it is a dimension. Grouped-query attention is standard attention at a smaller KV width: same formula, different value.

Verified The rule catches a case already in the tree. BLIS charges Kimi-K3's 69 linear-attention layers through the existing full-attention coefficients, substituting head width for the context dimension, and folds the recurrent-state bandwidth into the per-layer overhead. That is the dimension treatment applied to a formula-shape difference. It is documented in-tree as knowingly lossy, and the rule would have flagged it in advance.

Cited The rule also matches how practitioners reason. The llm-d GLM-5.2 study (§5) avoids tensor parallelism because the latent cache cannot be sharded: it stores one fused latent rather than separate KV heads, so at TP 8 every rank keeps a full copy. That is a formula-shape difference, not a smaller kv_width, which is why mla_attention is its own operator rather than full attention at a different dimension.

The practical consequence: a new architecture era adds an operator, roughly once per era rather than once per model. Everything between eras is a new set of layer groups.

§4Evidence

One quantity, three definitions

BLIS currently computes one physical quantity three different ways. An operator basis would make that impossible.

Verified BLIS has three definitions of latent-attention KV width. Two of them differ in shape, which is the sign-flipping defect below; the third is a two-byte constant in the default backend where the others read the configured dtype. The capacity path uses the compressed latent, kv_lora_rank + qk_rope_head_dim, replicated across tensor-parallel ranks. The step-time path, in both latency backends, uses a grouped-query shape divided by the product of tensor and data parallelism. KVLoraRank appears in neither step-time model. Nothing makes the two agree.

Because one divides by that product and the other does not, the error is not a constant bias. Its sign changes with parallelism.

Consequence

At the wide expert-parallel shapes this model family deploys at, BLIS under-charges the dominant decode term. Both the reference documentation and the runtime warning state, without qualification, that step time is pessimistic for these models. In the deployed regime that is the wrong direction, and it makes a capacity plan look safer than it is. Filed as #1712.

Verified That last pair is the third definition. Trained-physics hard-codes a two-byte KV element; roofline reads the configured width. So --kv-cache-dtype fp8 halves the element for the capacity path and for roofline’s step time, and leaves trained-physics — the default backend — unchanged. A run can double its KV-block capacity and see no step-time effect at all.

Three divergences in the comparison above: the factor of two, the head width, and the divisor. Only the divisor makes the sign flip, because it is the only one that varies with the deployment.

Inter-token latency keeps falling with parallelism because the KV-read term is divided by it. The true latent read does not shrink, so this is the defect showing through to a reported metric.

An operator basis makes this state unrepresentable. Latent attention as one operator has one KV-width definition, used by both capacity and step time. §9 states this as invariant NS-2, so the agreement is tested rather than assumed.

§5Target

Target architecture

Proposed Four layers, ordered by how often each changes. A change should be absorbed by the highest layer that can express it.

Catalog data, changes daily

Models as layer groups, families, hardware, networks, storage devices, clusters, workloads, SLO classes, scenarios, candidate sets, runtime recipes, config-key vocabulary. Versioned, strictly parsed, no Go.

Performance registry learned data, changes per campaign

Cost models: per-operator corrections, scoped, with uncertainty. Behaviour models: acceptance rates, hit rates, residency transitions. Immutable releases with validity domains.

For any incoming change, in order. Descend only when the layer above cannot express it.

Two constraints on this split

Operator corrections are not hardware-blind. Verified The tensor-parallel communication correction absorbs an on-package-link to memory-bandwidth ratio, which is per-GPU. Keying it blind would contradict the current calibration.

Named blocks are a correctness fix, not a preference. The length-switching behaviour above means appending a coefficient silently changes which formula runs. Named blocks remove that.

An independent check: the llm-d GLM-5.2 deployment

Cited In July 2026 the llm-d team published a measured study of GLM-5.2 agentic serving on H200: parallelism sweeps, prefill/decode ratios, KV offloading, and multi-token prediction, on the same Weka agentic trace corpus BLIS reads. It is entirely measurement-based, with no simulation.

Four findings bear on this design.

The latent cache is replicated across tensor-parallel ranks. Their reason for avoiding tensor parallelism at all is that latent attention stores one compressed latent rather than separate KV heads, so it cannot be sharded: at TP 8, eight ranks each keep a full copy. That is the physics the BLIS capacity path already implements and the step-time path contradicts (§4). It also means the defect bites hardest in exactly the regime this model family deploys in: their reference topologies are TP 1 with data and expert parallelism 8 or 16, so TP·DP is 8 to 16 and rising, which is where the charged value crosses the truth.

KV capacity is the binding constraint, not compute. They state it directly for GLM-5.2, and their per-node capacity comparison shows the size of the effect: 598K logical tokens at TP 8 against roughly 1.77M at DP 8 and 5.2M at DP 16. A simulator whose KV width is wrong by a factor that changes with parallelism will get the binding constraint wrong first.

Acceptance is a per-position behaviour, and it was measured. GLM-5.2 drafts three tokens; acceptance is about 80%, 65% and 52% by draft position, with an aggregate of 64.0 to 70.5% stable across two input-length sweeps. This is exactly the shape §5 argues a behaviour model must hold, and it is why the registry example above cites the published values rather than an invented scalar. Today BLIS requires the operator to supply a single number.

The configuration search was manual. They enumerate topologies by hand and measure each one: 1P1D, 2P1D, 3P1D, 2P2D, 3P2D across 16 to 80 GPUs. Their conclusions are ordering statements of the kind a leaderboard produces — an extra decoder buys 21% output while an extra prefill replica cuts median time to first token 21% and restore traffic 94%; widen an instance before replicating it. D1 and D2 make that work cheaper, and their measurements are ground truth a leaderboard can be scored against.

Producer and artifact are separate on purpose

Two of the five pairs exist because the same layer has two different lifecycles.

blis-modelspec writes; blis-catalog holds. The extractor is code that changes when a vendor invents a new way to state its layers. The catalog is data that changes when somebody adds a model. The review question differs too: a catalog change asks whether this model is described correctly, an extractor change asks whether this translator handles the dialect.

blis-calibration fits; blis-registry publishes. This split carries a requirement rather than a preference. NS-5 says a leaderboard row must cite the registry release that produced it and state whether the scenario falls inside that release's fitted domain. That works only if a release is immutable and separately addressable. A research pipeline that changes freely cannot also be the immutable artifact, so a scenario pins a release, never a trainer commit. Implementing the registry as signed, append-only release artifacts of the calibration repository would satisfy this equally well; the guarantee is what matters, not the repository count.

The test this separation has to pass

Adding a model touches one repository. Swapping a fabric touches one repository. Refitting coefficients touches one repository and produces a new immutable release. Adding an operator touches two: the extension package, and one line of inference-sim to link it. Changing how a leaderboard renders touches one, and needs no simulator release. If any of those spans more, the boundary is in the wrong place.

The sweep driver stays in the simulator

Verified Enumerating a candidate set means knowing which combinations are valid, and that is BLIS-internal physics. Whether an expert-parallel group is legal depends on the effective group size and the expert count; whether a data-parallel degree is legal depends on the KV capacity it would leave per replica; a tensor-parallel degree has to divide the head count. Those rules live in the placement and capacity code. A harness outside the binary would have to reimplement them, and the two copies would drift.

So blis rank is a command in inference-sim: it enumerates, skips invalid combinations with a recorded reason, runs each seed, performs the load sweep, aggregates rows, and writes one artifact. The run-set state it holds lives for the duration of that command and is not simulation state, so the kernel stays a library that terminates.

What stays outside is everything after the artifact is written. blis-leaderboard never invokes the simulator; it reads artifacts. That keeps the boundary at a file format rather than a function call, which is the same choice made for the catalog and the registry.

Two leaderboards

§5 is machinery. This is what an engineer reads. Two rankings answer two different questions.

Configuration leaderboard: what should we deploy?

Ranks the valid combinations from the candidate set. Per row: sustainable throughput; TTFT and TPOT, aggregate and per SLO class; a normalised utility such as throughput per GPU; and a confidence. Per-class latency stays available behind the row, because an aggregate can hide a protected class being starved.

Calibration leaderboard: how should BLIS learn?

One fixed evaluation set, one candidate set; only the calibration pathway changes. It compares the analytic roofline, the globally-fitted trained-physics, zero-shot transfer, nearest-model priors, targeted active calibration and full calibration, judged by top-K recall, ranking regret, prediction error, uncertainty coverage, and the measurements or time each needs. It is deliberately not scenario-specific: a pathway that wins on one model may lose over the set.

This second board is what makes the first trustworthy. It measures whether BLIS finds the true top-K quickly, which is what cases 1 and 2 need. Ranking quality matters more here than point error: a model that predicts every latency twenty percent high but orders configurations correctly is more useful for a deployment decision than one with lower error and scrambled order.

Why the leaderboards depend on R1 and R2

Neither board can be built on a single global coefficient vector. A rank confidence needs a posterior with a validity domain, so the row can say the scenario lies outside what the fit covered. A calibration leaderboard needs a runnable fitting pipeline, so two methods can be compared at all. The confidence column is R2; the runnable fit is R1b, in Phase 2. That is why the configuration board can ship in Phase 1 and the calibration board cannot.

Cold start, end to end

The six cases compose into one path, and it is what the releases build toward.

  1. Parse the model artifacts.
  2. Build the layer groups.
  3. Transfer a zero-shot prior from the nearest known model, hardware and operators.
  4. Spend a few targeted measurements where they most reduce decision uncertainty.
  5. Sweep the candidate set.
  6. Publish the top-K with confidence, and update the posterior from production telemetry.

Steps 3 and 4 are what make this learning rather than brute-force benchmarking. Both depend on uncertainty being real rather than decorative.

Two capabilities assumed above that BLIS does not have

Verified BLIS reports achieved throughput, not sustainable throughput. The current metric is completed work divided by run duration at whatever rate was offered. A column headed "sustainable throughput" needs a load sweep that finds the maximum rate meeting the SLO classes. The peak-rate saturation detector is adjacent but answers a different question: it classifies whether a given run saturated, and deliberately needs no capacity estimate. There is also no sweep driver: BLIS evaluates one configuration per invocation. Both are D1 work, and neither is blocked by the operator basis.

7.2 Value-preserving extraction and recalibration are different projects

This is the decision that most affects sequencing.

Verified The existing coefficients were fitted against the current aggregate expression, including the maximum-of-compute-and-bandwidth form and the grouped-query KV width that §4 shows to be wrong. So the work divides:

  • Value-preserving: factoring the existing expression into named operators, one at a time, gated on byte-identical output.
  • Recalibration: fixing latent-attention KV width, giving linear attention its own operator, adding sparse_indexer and windowed_attention. These change output by construction. Each needs a refit.

8.4 Cost expressions: how a timing estimate is put together

Every duration BLIS estimates is produced the same way. Naming that way, and holding to it, is what makes a coefficient auditable, a registry release swappable, and a contribution report exact rather than approximate. The shape below is not a proposal: Verified it is what the shipped code already computes, in a form that has never been written down.

A cost expression has four declared parts.

The arithmetic is then a dot product, and nothing else:

cost = Σ φi · βi

Separability

Proposed φ depends on the scenario and the catalog. β depends on the registry. Neither reads the other. This is stronger than saying the model is linear in its coefficients, and it buys three things linearity alone does not. A registry release can be swapped without recomputing φ, so re-ranking under a new fit is a re-dot rather than a re-run. Two releases that disagree on a row provably disagree about a coefficient, not about a feature. And scope checking becomes elementwise: a run is an extrapolation exactly when some feature it actually exercised carries a coefficient fitted outside the run's configuration.

Verified Separability holds today for every coefficient value. Four independent sweeps of the non-test sources in sim/latency/ find no coefficient value compared, branched on, or used in a conditional; all seven conditionals mentioning a coefficient test a slice length. The consequences of that exception are §4's subject and R2's first task.

Nonlinearity belongs inside a feature, never between features

The roofline crossover looks at first like a counterexample. It is not. Written out, the prefill term is

βprefill · max(tcompute, tkv)

where t_compute and t_kv are intermediates inside the feature map, not entries in φ. Both are computed from token counts, model dimensions and hardware rates. The max reads no coefficient; the coefficient multiplies its result. So this is one feature whose feature map contains a max, the dot product is strict, and separability is untouched. The same holds for the roofline backend's single global crossover.

Proposed The practical rule: a max may combine intermediates; it may never combine features. A max placed between two features would assert that the two quantities are equally efficient, which is precisely the assertion a second coefficient exists to remove.

Rates and corrections enter differently

Two kinds of number come out of a registry release, and conflating them is how a design acquires a corner case.

A rate is consumed inside the feature map; a correction multiplies a finished feature. The distinction is forced by the max: a divisor cannot be factored out of one.
KindEntersExamples
RateInside the feature map, as a divisor or scalemfu_prefill, mfu_decode, bw_peak_tbs, cross_node_hop_latency
CorrectionOutside, as a coefficient in the dot productprefill_compute, tp_allreduce_attention, per_step_overhead

This makes the roofline backend's place in the design honest rather than forced. It has no step-time corrections at all — Verified zero reads of a β coefficient — but it is not coefficient-free: it owns two achieved-utilisation rates and three request overheads, and cites three datasheet quantities. What is uniform across backends is the feature map; the dot product is what the trained-physics backend adds on top. Describing roofline as a degenerate dot product with a coefficient of one would be a fiction, and the fiction would have to be maintained.

What the registry may select, and what it may not

Proposed A coefficient set may determine which features exist, because a set that declares a feature the code can emit is asking for a different, explicitly named model. A coefficient value may never determine which features exist. Stated as one line:

φ = featureMap(scenario, catalog, feature_names)   // names, never values

The distinction is not academic. §4 shows a shipped case where a coefficient array's length selects between two formulas that differ by a factor of 1.67 on memory-bound traffic and agree exactly on compute-bound traffic — a divergence that a golden dataset can therefore fail to notice.

Clamps sit outside the expression

Two adjustments are applied after the sum and are not part of it: an integer truncation with a floor of one tick, which guarantees the simulation clock advances (INV-3), and the LoRA adapter factor, which multiplies a finished step time. So the full statement is

raw       = Σ φi · βi                       // float64, exact
scheduled = max(1, int64(max(1, int64(raw)) · f))  // f = LoRA factor, ≥ 1

A reconstruction test must therefore assert against raw, in floating point, and treat the clamps as a separate stage. Asserting against the scheduled value would fail on any batch small enough for the floor to bind, and the temptation would be to loosen the test rather than the statement. Verified the truncation happens before the LoRA multiply, so the factor scales an already-rounded value; that quantization is inherited, not introduced here.

Two consumers, because some real costs do not block

Not every modeled duration delays anything. Streaming detokenization and post-decode overhead are real per-token and per-request costs, but they model host work that does not occupy the accelerator, and Verified the shipped simulator deliberately lets them inflate reported end-to-end latency past the request's own completion event.

Proposed Turning those into events would force a choice between two wrong answers: delay the request, which changes the physics by making detokenization block the engine; or schedule an event that does nothing, which is heap cost for no behaviour. Hence two consumers of one expression.

Both consumers use the same expression, the same registry and the same provenance. They differ only in what happens to the scalar.
ConsumerEffectCost kinds
ScheduleThe scalar becomes a future event timestampStep time; queueing delay; adapter load; prefill/decode KV transfer
AccrueThe scalar attaches to a request or metric; no queue entryPer-output-token processing; post-decode overhead

The consumer is a property of the cost, not a configuration choice. Whether detokenization blocks the accelerator is a question about the machine, and a flag that could flip it would let configuration change the physics. The binding is configurable; the consumer is declared.

Where the partition boundary falls

Proposed Feature names are qualified by the event they belong to, so that introducing a new kind of event adds features without renaming or refitting the existing ones. The boundary is the event, and it is worth being precise about what is not a boundary.

Verified vLLM schedules one forward pass over a mixed batch. Its scheduler output carries a single map from request to scheduled-token count and one total; one token budget is decremented by both the running and the waiting loop and asserted non-negative; and whether a request is prefilling is a per-request boolean derived from token counts, not a mode the batch is in. BLIS matches this exactly, with the same derived predicate. So prefill and decode are features of one event, not two events, and a per-step overhead is a per-forward-pass constant. Partitioning the feature vector by phase would model a distinction neither system makes.

What follows from the mixed batch is an identifiability constraint rather than a partitioning one, and §4 states it: four coefficients that always move together in the same forward pass cannot be separated by any fit over traffic of a fixed shape, however many names they are given.

§9Invariants

Invariants

Existing invariants that constrain this work

  • INV-6, determinism. The acceptance gate for every value-preserving step, and the reason for §8.3.
  • INV-13, run and replay parity. Operator and catalog resolution must agree on both paths; model-level inputs are re-supplied, not round-tripped through the trace.
  • INV-4, KV conservation, and INV-BC-DP1, dense step-time byte-identity. Unchanged. The latter is the established pattern for value-preserving extraction.

Proposed additions

NS-1 Operator model-blindness.

An operator's work and bytes are functions of its dimension inputs and hardware rates only, never of a model name, a config field name, or an architecture string.

Verification — a static test asserting that operator definitions reference no model identity.

NS-2 One definition per physical quantity.

Any quantity consumed by more than one path, KV width being the motivating case, has exactly one definition, used by all of them.

Verification — capacity and step time derive KV width from the same operator; a differential test across the parallelism matrix fails on divergence. That test fails today: its absence is #1712.

NS-3 Additive operators.

Introducing an operator leaves every model that does not use it byte-identical.

Verification — golden coverage across the committed model fixtures.

NS-4 Catalog completeness over panics.

A model whose config does not state a quantity in the expected form is resolved through a translator, or reported as a missing catalog fact. Never a hard abort on a field-name lookup.

Verification — the Nemotron-3-Ultra case runs.

NS-5 Ranks carry their validity domain.

A leaderboard row states the registry release that produced it, and whether the scenario falls inside that release's fitted domain. A rank from outside the domain is reported as extrapolation.

Verification — a scenario deliberately outside the fitted domain is labelled extrapolation rather than silently ranked.

NS-6 Model facts come from the catalog; deployment choices come from the caller.

A model runs if and only if it is in the catalog, and run time reads the catalog without ever writing it. Entries are authored by hand and committed. The catalog is a directory the caller names, with no default and no remote fetch. It holds what a model is; it does not hold GPU type or parallelism degree, which are deployment choices the caller states on the command line in R1 and in a Scenario or CandidateSet from D1 onward. Nothing about the model or the deployment is inferred.

Verification — an uncatalogued model is refused; a run missing a deployment input is refused naming the flag; and no run, replay, observe or rank creates or modifies a catalog file. Both halves fail today. The run-time path fetches a missing config and writes it into the catalog, so the catalog grows as a side effect of running. And a run with no --hardware or --tp warns and proceeds on a deployment nobody chose.

Scope — binds the command line, not the Go API. A library caller may construct a model configuration directly; 21 test files do. On the command line there is exactly one way to supply a model config, which is why --model-config-folder is retired rather than kept as a second path.

R1 establishes one property: a model runs if and only if it is in the catalog (NS-6). Everything below serves that. Each box names an observable result, not an activity.

Why this is the goal rather than tidying

Verified Today the catalog grows by accident. When a model is absent, the run-time path fetches config.json from HuggingFace and writes it into model_configs/, so running an unknown model adds a catalog entry as a side effect. That is why the two halves of the catalog drifted apart.

         # it did not refuse: it TRIED. Against a real public repo it
         # would have run, and left a new fixture behind.

R1 removes run-time fetching outright. At this scale onboarding is a person downloading a config.json and committing it, which needs no tooling. If a larger catalog makes that tedious, a fetch command belongs in R4b alongside the translators, which are the code that has to read a vendor config anyway.

How the simulator finds the catalog

The catalog is a directory on disk, named by --catalog or the BLIS_CATALOG environment variable. There is no default, no search path and no remote fetch. A run with neither is refused, naming both forms.

export BLIS_CATALOG=~/src/blis-catalog          # once, per shell
blis run --model glm-5.2 --hardware H100 --tp 8

BLIS_CATALOG=~/scratch/my-fork blis run ...     # explicit override,
                                                # visible in history

Two reasons for a local path rather than a URL. It keeps a citation checkable offline: a row naming a catalog revision can be verified with git rev-parse, where a remote could have moved. And it makes experimenting ordinary — clone the authoritative catalog, edit a config.json to try a hypothetical model shape, and run. No fork of the simulator, no pull request, no special mode. That is the "new models are data" property working.

Verified No default is deliberate. Today's --defaults-filepath defaults to defaults.yaml, resolved against the working directory, so blis run silently only works from the repository root. A relative default such as ../blis-catalog inherits that: an installed binary run from a home directory would resolve it to a sibling of the home directory. It also contradicts NS-6, which says nothing about the model is inferred.

A catalog entry is what a model is: its config.json, and the identity needed to fetch it. GPU type and tensor-parallel degree are not model facts. What is in a model.yaml, and why so little

A model entry is its config.json plus enough to say where that file came from. The config.json is copied verbatim from the vendor and never edited, so it stays diffable against upstream.

# blis-catalog/models/qwen3-14b/model.yaml
name: qwen3-14b
source:
  provider: huggingface
  repo: Qwen/Qwen3-14B        # case-sensitive; see C5
  revision: <commit-sha>        # what was downloaded
  retrieved: 2026-09-15

That is the whole entry. Two questions it answers, and nothing more: which model is this, and where did this config.json come from. Nothing reads source at run time once S6 lands; it exists so a person can re-fetch by hand, diff against upstream, and audit a result. A model with no upstream repository (openai/gpt-oss-120b, gpt-oss-20b) records that instead of a repo.

Repository setup, and one thing not to copy from the simulator

Verified The simulator's .gitignore ignores *.json and then whitelists 10 exceptions, including !model_configs/*/config.json. That works there because JSON is incidental. .gitattributes matters more than usual here

C3 says a vendor config.json is committed verbatim so it stays diffable against upstream. Git's line-ending normalisation can rewrite it on checkout, which breaks that property silently on Windows.

# Keep authored YAML diffs readable and stable across platforms
*.yaml text eol=lf
*.yml  text eol=lf

The corpus exists only as 5.0 GB of untracked local files, 22 of which exceed GitHub's 100 MB hard limit. Committing the sources alone will not make the coefficients reproducible — R1b needs a storage decision for the corpus, or a derived compact fit input, and its acceptance test (a clean checkout regenerating the coefficients bit-for-bit in CI) cannot pass without one.

Training does not belong in inference-sim. The pipeline is already a process boundary — it shells out to the blis binary and shares no Go types — so the branch should migrate to blis-calibration when that repository is created, rather than being ported to main first. This is left as an open question for R1b, not a Phase 1 task.

Conclusion: R1's stated purpose — one unambiguous catalog, and a deployment that is chosen rather than inferred — is achieved. Once #1771 deletes the bundled tree, the third copy and the transition fallback go with it, and a model runs if and only if it is in the catalog holds without qualification. R2 may begin on that assumption. Two carry-forwards, neither blocking: the catalog CI gate (#1750), whose scope covers the hardware, workload and device namespaces R2 also touches and should be reconciled with R2 rather than duplicated; and the reproducibility floor, which is R1b's in Phase 2. The one claim to stop making in the meantime is that Phase 1's coefficients are reproducible. They are transcribed, and a registry release must state it.

R2 in one page

The problem. Every number BLIS uses to estimate latency is authored somewhere that cannot say where it came from. Eleven learned corrections live in one positional array whose length silently selects which formula runs — and the two formulas it selects between differ by two-thirds on memory-bound traffic while agreeing exactly on compute-bound traffic, so the divergence hides from goldens. A fabric's bandwidth is filed under a GPU, so the same chip on two networks is unrepresentable. Two repositories ship the same hardware table and have already drifted on a real value, leaving a wrong peak-FLOPs figure in the simulator today. One array position is read as two different physical quantities by the two backends. And the provenance of every borrowed number — the MFU values that set roofline's whole compute estimate, the vendor bandwidths, the expert-parallel coefficient copied from its sibling — lives in a YAML comment that no run can read and no report can cite.

The change. Each number becomes a block with four required fields: its value, its units, how it was obtained (method), and the range it holds over (scope). Calibration inputs split by owner: chips and fabrics to the catalog, inferred numbers to a new blis-registry. Both latency backends draw from it, so roofline and trained-physics become two named coefficient sets rather than two code paths.

The discipline. §8.4 states the law R2 implements: a cost is a feature vector dotted with a coefficient vector, the features come from the scenario and catalog, the coefficients from the registry, and neither reads the other. Authored files state physical units — bandwidth, latency, bytes — and BLIS derives block counts and ticks. Declared facts go to the catalog; anything a measurement would revise goes to the registry. R2 reports what it knows (method, scope status, each coefficient's share of the estimate) and invents nothing: no confidence score, and no new coefficient values. Every task is gated on byte-identical output.

Provenance: recording what we already know

R2 turns those comments into fields. The design constraint is that BLIS will always hold numbers of several kinds at once: new accelerators and fabrics arrive faster than calibration campaigns, and some inputs (a vendor's peak bandwidth) are not ours to measure at all. The purpose is not to eliminate the mixture but to make it legible, so that a number's origin reaches the report instead of stopping at a comment.

Each entry therefore records two orthogonal facts. How the number was obtained (method), and whether a fit ever treated it as a free parameter against its own term's traffic (fitted). Separating them resolves a real ambiguity: a value copied from a fitted sibling is, in one sense, fitted — but not against the traffic of the term it now prices, which is the fact that matters when deciding whether to trust it or go measure it.

What R2 reports, and what it does not

R2 reports facts about inputs: which coefficient set a run used, each coefficient's method and fitted flag, whether the run fell inside each one's declared scope, and each one's share of the estimate. It introduces no confidence score and no posterior. Turning those facts into a calibrated confidence needs a reproducible fit and a held-out evaluation, neither of which exists in Phase 1; attaching a number to the word confidence before then would invent precision. NS-5 is satisfied the same way it is stated: an out-of-scope result is labelled an extrapolation rather than given a confidence.

Uncertainty: recorded when it is known, not manufactured

An interval is optional in R2, and the reason is worth stating rather than hiding in the schema. For a measured coefficient an interval is a regression output — but the fit that produced the shipped betas is unreproducible (the pipeline exists only as bytecode; see R1b), so BLIS cannot emit intervals for its own measured coefficients yet. For every other method an interval is a human judgement about transfer, which is worth recording when someone is prepared to defend it and worth omitting when nobody is.

So R2 accepts ci95 where it is genuinely known and does not require it anywhere. A missing interval is honest; a fabricated one is not. R1b makes intervals derivable for the measured entries, and a later release may require them once they can be produced. Two properties hold regardless. A non-measured interval is normally wider than a measured one. And an interval never substitutes for scope: a tight interval used outside its scope is still an extrapolation, because an interval describes uncertainty in the number, not applicability to the case.

The rule that sorts them. The catalog holds BLIS's representation of declared facts: what a model is, what a chip can do, what a fabric can do. Someone wrote them down, and they are true by specification. The registry holds inferred numbers: corrections, efficiency factors, overheads — things estimated from data, where a better experiment yields a better value. Both need provenance and scope; only registry numbers need a fitted flag, because only they could have been fitted.

Two tests make the rule decidable when a number looks like it could go either way, and the transfer costs above are exactly that case.

The units test. A number in physical units that a datasheet could state — GB/s, TFLOPS, µs, bytes — is describing the world, so it is a catalog fact. Everything else is describing BLIS's model of the world, so it is a registry estimate: a dimensionless factor (a correction, an efficiency, an achieved fraction), a simulator unit (blocks per tick), or a per-structure rate (µs per layer, µs per request). This is why the two transfer pairs split despite sharing a name: 25 GB/s and 0.05 ms are fabric specifications, while 100 blocks-per-tick has no counterpart in any datasheet. It is also why the dimensionless MFU factors leave the hardware file while the TFLOPS figure beside them stays.

Authored inputs are in physical units; simulator units are derived, never stored

Verified A simulator unit in an authored file is a design smell, because it fuses facts that belong to different owners. --kv-transfer-bandwidth 100.0 blocks-per-tick multiplies three independent things into one number nobody can revise separately: how fast the device is, how big a block is, and how long a tick is. Device speed belongs to the hardware; block size is model-dependent (it follows KVBytesPerToken, which differs between an MLA model and a GQA one); tick scale is an implementation detail. Authoring their product means a new model silently changes the meaning of a number that was supposed to describe a bus.

The modern offload path already does this correctly, which is the precedent R2 generalises rather than an idea it invents. The catalog states the device in physical units; BLIS derives the rest:

The substitution test. If replacing the number with a vendor's published figure would be correct, it is a catalog fact. If it would be a category error — because the number absorbs modelling residue that no datasheet reports — it is a registry estimate. β₄ fails this test by construction: it absorbs an NVLink-to-HBM ratio and whatever the fit could not otherwise explain, so no published number could replace it.

The two MFU values are the case that tests the rule, and they are why the inventory above splits one hardware file across two homes. They sit beside TFlopsPeak and look like chip properties, but the two differ on every question the rule asks. TFlopsPeak is 989.5 because NVIDIA says so; no experiment of ours changes it. mfuPrefill is 0.45 because somebody read a training-workload figure of 55–60% and discounted it for inference (#589); a serving-workload measurement would change it tomorrow. One is a specification, the other an estimate that happens to be filed among specifications.

Two numbers that are NOT coefficients, and must not be treated as such

Speculative acceptance rate (--speculative-acceptance-rate) is a required user input, not a learned value: it describes the workload and draft model in front of you, and BLIS deliberately refuses to guess it. Making it a registry entry would imply a default exists. It becomes a behaviour model in D3 — something BLIS could learn per model and runtime — but never a coefficient.

Policy thresholds (--pd-prefix-threshold 16, the saturation detectors' knobs, queue-depth limits) are configuration: they set what the simulated system does, not how expensive its physics is. The PD threshold's default of 16 is copied from llm-d's shipped config, which makes it a well-sourced default for a policy, not an estimate of anything. These stay CLI and scenario inputs. The test is whether a better experiment would change the number (registry) or whether an operator would change it to get different behaviour (configuration).

What R2 therefore takes, and what it leaves. Into the registry go the inferred numbers: the request-overhead alphas, the step-time betas, the LoRA adapter costs, and the legacy CPU↔GPU transfer pair — each becoming a coefficient set with provenance and scope. Into the catalog go the declared facts: Hardware splits from Network, and the PD fabric figures join the Network object beside inter_node_bw_gbps, where a bandwidth in GB/s belongs. The storage-device table stays where #1770 already put it, correctly, and gains only provenance fields.

Both moves fix the same defect from opposite sides. --pd-transfer-bandwidth 25.0 carries NIXL RDMA default in its flag help and --kv-transfer-bandwidth 100.0 carries nothing at all: one is a fabric specification and the other a modelling choice, and today both are Go literals that no output can cite. R2 gives each a home where its provenance is a field — and the two homes differ, which is the point of the rule.

What the LoRA coefficients are, and whether they are needed

Verified They price the three costs a served LoRA adapter adds, and they are inert unless a run declares adapters — defaults.yaml marks the block INERT and omits adapter_capacity, so a run without adapters is byte-identical to a build before the feature (INV-6).

  • load_base_latency_us + load_bandwidth_bytes_us — the cold-load cost of pulling an adapter's weights into HBM when a request needs one that is not resident. A fixed cost plus bytes over a rate.
  • footprint_bytes_per_rank — the HBM an adapter occupies, linear in its rank. It reduces the memory available for KV blocks, so it changes capacity, not just latency.
  • step_overhead_tiers (k6, k7 per rank) — the per-step compute penalty of running a batch with adapters, as a multiplier ≥ 1.0 on step time. k6 scales with how many distinct adapters are active in the batch; k7 normalises per rank tier. Batching requests across many adapters costs more than batching within one, which is the effect these capture.

Are they needed? For a run with no adapters, no: the whole family is unreachable. For multi-tenant adapter serving — the case the family exists for — they are the only thing that distinguishes it from base-model serving, and dropping them would model adapter switching as free. So they are needed conditionally, which is exactly what a coefficient set with a declared backend expresses: a set an adapter-serving scenario names, and nothing else loads.

What makes them a registry concern rather than a footnote is their provenance. They are the only numbers in BLIS derived from an external Digital Twin, rather than from our own runs or a vendor specification. The fidelity work behind them validates one leg and not the other: compute overhead holds to ≤20% MAPE on two model configurations, while the absolute-TTFT leg is bounded but unsupported. The reason is structural — BLIS ports adapter deltas onto its own separately-calibrated base, which differs from the Digital Twin's. That is a scope statement and a method statement of exactly the kind R2 introduces, and today it exists only as prose in a design document. A registry holding only step-time coefficients would leave a second calibration source with the precise problem R2 was built to fix, one file away from the fix.

Three rules keep this honest, and they are what a third backend will rely on. A backend declares the coefficient names it consumes, so a set that omits one is refused by name rather than defaulting silently — the same failure R2 removes from the positional array. An absent coefficient and one set to zero are different statements: absent means the backend does not price that term, zero means it prices it at no cost, and the second needs method: not_charged to say so deliberately. And a set may extend another, inheriting entries it does not override, which is how trained-physics reuses roofline's hardware inputs without copying them.

A run may use more than one set, and the design must say so. --prefill-latency-model and --decode-latency-model already let a PD deployment run one backend for prefill and another for decode, so a 3P–6D run can legitimately pair a roofline prefill pool with a trained-physics decode pool. A set is therefore selected per pool, not per run: the scenario names a default and a pool may override it, exactly as it overrides TP today. The results file records the set each role used, so two halves of one experiment stay distinguishable. The existing guard stands — with DP or EP active a non-trained-physics pool is refused, because it would model no DP/EP step-time effect while the rest of the cluster does.

Four consequences follow, and they are why this is R2 work rather than a later tidy-up. A run states which coefficient set produced it, so two leaderboard rows using different backends are distinguishable rather than both labelled by model and GPU alone. Roofline's borrowed MFU values acquire the same provenance and scope discipline as the betas, closing the gap where the analytical backend looked calibration-free because its inputs were undocumented rather than absent. When R3 unifies both backends onto one operator set, the registry already keys by backend, so no re-plumbing is needed. And a new backend is a new set over the shared bases — it may add coefficients, inherit them, drop them, or zero them, and it needs no registry schema change to do any of it.

Single-node and multi-node, for TP and for EP

That is the right design, and it is already built. But it is built for one of the two collective groups, and the asymmetry is worth stating plainly before anyone reads a multi-node expert-parallel number.

What R2 changes, and what it does not. R2 adds no cross-node physics — that is not a coefficient problem, and §14 assigns the inter-replica pricing gap to D3 alongside the under-charged decode KV term that compounds it. What it does is make the four cases distinguishable in the output. Today a multi-node EP run and a single-node EP run produce two numbers with no recorded difference in standing; after R2 the first records moe_dispatch with scope: {nodes_spanned: [1]} violated, method: copied, moe_comm_scale at method: assumed, and αhop not_charged — four recorded facts that together say this multi-node expert-parallel estimate is the weakest number on this page. That is the difference between a warning somebody has to notice and a field a leaderboard row must carry.

Granularity is not the constraint; identifiability is. Two coefficients that always move together cannot be separated by any fit, however many names they have. R2 makes them addressable and leaves to a fitting campaign the question of which are separately determinable.

Why R2 names these but sets no values

Verified The cross-node cost has two halves that are collinear on traffic of a single shape: a bandwidth term scaling with bytes (β₄, through the placement-derived span penalty) and a latency term scaling with hop count (αhop). Both grow with node span. A fit on one workload shape will split them arbitrarily and report a good loss for the wrong reason. This is why αhop ships at zero on all five GPUs rather than at a plausible constant, and why the existing guard requires it to come from an independent NCCL microbenchmark rather than be back-solved from a residual.

R2 names both, scopes both, and leaves their values alone. Which are separately identifiable, and from what traffic, is a question for the fitting pipeline in R1b.

Scope, and the cost of saying so too often

A coefficient's scope is the range it is known to hold over. Reporting when a run falls outside it is the point of the field — and a naive implementation of that reporting would make BLIS unusable. Today's single global fit was made on one cluster, so most runs fall outside some declared scope, and a per-coefficient warning per run would produce a wall of text that trains users to ignore warnings. That is a worse outcome than silence, because it also buries the warnings that matter.

So the reporting obeys three rules, and they are part of the design rather than an implementation detail:

1. The results FILE always records the full per-coefficient detail.
   Machine-readable, complete, no thresholding. This is the audit trail.

2. Stderr emits AT MOST ONE summary line per run, naming the largest
   contributor that is out of scope or not measured -- not one line per
   coefficient:

     note: 3 of 14 coefficients are outside this run's scope; the largest
           is moe_dispatch (23% of step time, method=copied). Full detail
           in results.json. Re-run with --explain-coefficients for a table.

3. A coefficient contributing less than 1% of the estimate is never the
   subject of a warning. It stays in the file; it does not interrupt.

The contribution measure below is what makes rules 2 and 3 possible: without it, every out-of-scope coefficient looks equally urgent.

Which coefficient carried the estimate

Whether a run's weakest input is a problem depends entirely on how much that input mattered. A coefficient contributing 0.1% of step time and one contributing 60% deserve different attention, and no property of the registry can distinguish them, because contribution is a property of the run: it depends on the model, the batch and the placement.

Verified The decomposition is free. Trained-physics step time is already a sum of named terms, one per coefficient (trained_physics_model.go:873):

stepTime := prefillTerm + decodeTerm +
    m.Beta[2]*tWeight +
    m.Beta[3]*(tTpAttention + tTpDenseFFN + tMoEReduce) +
    m.Beta[10]*tMoEDispatch +
    m.Beta[4]*L + m.Beta[5]*batchSize + m.Beta[6] + ...
// each addend IS one coefficient's contribution: accumulate the addends
// already being summed, and divide by the total. No term needs extracting.

This is distinct from R3's per-operator error attribution, and the two are easy to confuse. R2 reports which coefficient is load-bearing (its share of the estimate). R3 compares against observed latency to report which operator is wrong. A coefficient can carry 60% of a run and be perfectly accurate; another can carry 2% and be badly wrong.

Together with provenance, the contribution answers a question BLIS cannot currently answer: which single measurement would most improve this estimate? Rank the coefficients by share, keep those whose fitted is false or whose scope excludes the run, and take the top one. That is a sort over recorded facts, not a judgement.

How tests get their numbers

R1 answered this question for model configs by keeping three fixtures under testdata/ and proving, through the real loader, that each parses to the same ModelConfig as the catalog entry that replaced it. That was deliberately transitional: its own comment says the gate goes away once the fixtures do. Coefficients need a different answer, and the reason is visible in the tree today.

The copy-the-values approach has already drifted, silently

Verified The shipped coefficients exist in two places: defaults.yaml and the golden fixture testdata/trained_physics_iter29.json. They no longer agree.

defaults.yaml   11 betas  [..., 1.94710771, 0.752037]   # beta_EP explicit
golden fixture  10 betas  [..., 1.94710771]              # beta_EP absent

The numbers agree elementwise as far as the shorter array goes, so every test passes. But array length selects formula shape, and an absent eleventh value is back-filled from the fourth — so the golden test exercises the back-fill path while production exercises the explicit one. They agree today only because βEP == β₄ by construction. The day βEP is refitted independently, the golden test silently validates a different model than the one BLIS ships, and nothing reports it.

This is the length-as-formula-switch hazard of Problem 1, reappearing as a testing defect. Copying coefficient values into testdata/ does not merely risk drift; it has already drifted. R2 fixes it in task N6: delete the second copy, re-point the goldens at the registry by name, and add a static guard so a coefficient array cannot reappear outside blis-registry.

So R2 does not copy coefficients into fixtures. The registry makes a better answer available, and it rests on one property: a set is immutable and addressable. A test names the set it wants, and names are cheap where copies are not.

Every defect found is the same defect. Detailed example — what R2 buys, and how to check it
Today: three things you cannot express

First, the same GPU on two fabrics. Verified InterNodeBwGBps lives inside the H100 entry, so an InfiniBand cluster and a RoCE cluster cannot both be described (#1662):

A literature-derived entry, written down

This is the shape of an entry BLIS already ships, with its provenance moved from a comment into fields. The reasoning is required because it is what makes the entry reviewable:

mfu_prefill:
  value: 0.45
  units: dimensionless
  method: literature
  fitted: false
  scope: {hardware: [H100]}
  sources:                     # a LIST: the value is triangulated,
    - kind: discussion        # not copied from one figure
      cite: "inference-sim#589, Roofline Physics Model: Evidence"
      role: primary
    - kind: publication
      cite: "FlashAttention-3 (Shah et al. 2024): 75% MFU, attention only"
      role: upper_bound
    - kind: publication
      cite: "NVIDIA MLPerf Training v3.1: 55-60% MFU, GPT-3 175B"
      role: supporting
  rationale: >
    Training reaches 55-60%. Inference lacks backward-pass optimisation,
    mixes compute- and memory-bound phases in prefill, and has variable
    batch sizes, so 0.45 is taken as a conservative inference figure.
  ci95: null                  # no interval claimed: none is known
  supersedes: null

A reader can disagree with the discount from 55% to 45% because the argument is on the page, and can see which source bounds it. When somebody measures MFU on an H100 under a real serving workload, this entry is superseded by a measured one and every result that used the old value is identifiable by set.

sources is a list because the realistic case is triangulation: a published figure, a bound, and often a few of our own runs that agree but are too sparse to fit. Recording all of them keeps method honest — partial evidence of our own strengthens a literature entry without making it measured, which requires a fit. A single-source entry is a list of one.

R2 task checklist — per repository, in dependency order

R2 establishes one property: every number a latency estimate depends on states where it came from and where it holds, and no number changes value. Each box names an observable result. Tasks are lettered per repository: G for blis-registry, H for blis-catalog, N for inference-sim, W for the published writing. (The release names D1–D3 are taken by the decision-surface track, so documentation tasks take W.)

Why this ordering

The registry schema is the contract the other repositories write and read against, so it is fixed first, on paper, against every number R2 touches: three alphas, eleven betas, nine LoRA cost terms, four transfer figures, and eight hardware values. The catalog split follows, being data movement with an exact arithmetic identity behind it. The simulator changes last and carries the byte-identity gate. Documentation is a gate, not a follow-up: R2's product is a claim about what a number means, and an unexplained claim is undelivered.

Does R2 split into two releases?

No, and the rules are what decide it. R2 is value-preserving, and acceptance #1 is byte-identical stdout — so the only seam that would justify splitting is between tasks that preserve stdout and tasks that change it. Applying that test, all but one task preserves it. The relocation-and-naming tasks are byte-identical by construction; those that add output (N3's scope status, N4's provenance and contribution, N8's identifiability record) write to the results file and one line of stderr, neither of which is the byte-identical stdout channel. The three documentation tasks change no code.

The exception is H4, and it is an exception on purpose. Reconciling the two hardware tables fixes a wrong L40S FP8 figure, which changes L40S roofline output. It is not a relocation, so it cannot hide under a byte-identity gate, and it is not a recalibration either, so deferring it to R5 would leave a known-wrong number shipping for two more releases. It is therefore carved out explicitly: one GPU, one field, one direction, gated on its own and announced. Every other GPU stays byte-identical, and that is what N5 asserts. A release that is value-preserving except where it repairs a value, and says so is more honest than one that either hides the repair or postpones it.

So a split would cut along task count rather than along a property, which is not a reason the rules recognise. R2 is larger than R1 because it touches three repositories and every family of learned numbers at once — but it is one coherent claim: every number states where it came from and where it holds, and none of them changes. Splitting it would produce a first half that reorganises numbers without reporting them and a second half that reports facts the first half has not finished establishing.

If delivery-size pressure demands a cut anyway, the honest seam is G1–G4 + H1–H3 + N1–N2 + N5–N6 (the registry, the catalog split, and the readers) from N3–N4 + W1–W3 (the reporting surface and the documentation). That boundary is defensible because the second group is the only part a user can observe. It is not, however, what the value-preserving rule asks for.

The invariant that governs every task

R2 is value-preserving, with one declared exception. Every task but H4 is gated on byte-identical stdout, on both backends. The gate is not a formality: it is what proves that relocating every determined number in the system perturbed none of them. Verified Counted from source, that is 38 values for a single GPU — 3 request-overhead alphas, 11 step-time betas, 9 LoRA terms, 5 chip facts, 2 achieved-utilisation factors, 2 fabric bandwidths, 1 per-hop latency, 2 legacy transfer figures, 2 PD transfer figures and 1 communication scale — and 78 across the five calibrated GPUs, since the last four families are per-GPU. The 15 storage-device values already live in the catalog (#1770) and only gain provenance fields. Work that cannot be done byte-identically is not R2 work; it belongs to R5 (recalibration) or R1b (a runnable fit) — with the single exception of repairing a number already known to be wrong, which H4 does for one field of one GPU, under its own gate and its own announcement. The test for admitting such a repair is narrow: the correct value must already be established and written down elsewhere, so that the change is propagation rather than judgement.

Worked case: why PCP is a scope key, not an R2 flag

Verified Parallelism dimensions arrive from upstream, and this is the case that shows what the open key set is for. vLLM's MoE group is dp × pcp × tp (fused_moe/config.py:1127), where PCP is prefill context parallelism — it shards prefill sequence computation and does not change the KV-cache shard count. Its decode-side sibling, DCP, is a separate axis. BLIS assumes PCP=1 and says so at both group-size accessors (sim/config.go:440, sim/expert_placement.go:31).

The assumption is safe today rather than merely convenient: vLLM refuses PCP>1 together with DP>1 (config/parallel.py:548), so no expert-parallel deployment can have PCP>1. BLIS needs no guard mirroring that exclusion, because BLIS declares no PCP input to constrain. But the upstream refusal is temporary — the message reads does not support data parallelism yet — so the day vLLM lifts it, BLIS's TP·DP group under-counts by the PCP factor.

Why not simply add a --pcp flag here? Because the flag and the physics are separable, and only one is R2 work. A flag defaulting to 1 is inert and could land byte-identically. A live PCP changes the MoE compute divisor from TP·DP to TP·PCP·DP, which 23 call sites read, and that changes step time. R2 is value-preserving, so the physics belongs to a release that declares itself output-changing — the precedent being EP, where --enable-expert-parallel existed before #1548 made it step-time-live. What R2 owes PCP is the scope key: a set fitted at PCP=1 says so, and a future PCP>1 run is labelled an extrapolation rather than silently priced with a divisor short by the PCP factor.

Why this matters beyond tidiness

R2 makes BLIS able to say, per number, whether it was measured here, borrowed from someone else's measurement, copied from a sibling, or not charged at all — and how much that number mattered to the answer. Those facts already exist; they are in YAML comments across two repositories, where no run can read them and no report can cite them. Recording them is the precondition for every claim downstream: a leaderboard row that can be audited, an extrapolation that announces itself, and a calibration campaign that can be pointed at the input that would help most rather than at the model as a whole.

§12Validate

Validation strategy

Correctness. Value-preserving releases are gated on byte-identical output over the committed model fixtures and the parallelism matrix, the mechanism INV-BC-DP1 established. NS-1 is a static test; NS-4 and NS-6 are end to end. NS-2 is a differential test between capacity and step time across the parallelism product. It does not exist yet, which is why #1712 went unnoticed; R5 writes it.

Fidelity. Recalibration releases are validated against observed runs through the existing observe, replay and calibrate loop, reporting per-operator error rather than one aggregate. Each closes a named documented approximation and states its scope: which models, which hardware, which parallelism range.

Decision quality. The calibration leaderboard is the validation harness for the decision surfaces: a ranking is judged by top-K recall and regret against measured runs, not only by point error.

Reproducibility. A released registry should be regenerable from committed sources and a pinned dataset. Verified That does not hold today. Phase 1 releases are therefore marked as transcribed rather than fitted, and R1b is what makes the guarantee real.

§15Open

Open questions

Unresolved on purpose. These are calibration and ownership calls, not design calls this note should make.

  1. Operator granularity for the linear-attention family. Distinct operators per recurrence is the position here, and shipped code supports it. Where the boundaries fall is a calibration question.
  2. Hardware-keyed operator corrections. Closed by observation during the R2 audit, and the answer was “neither”. The link ratio is not an input the step-time extractor is missing: the communication basis divides by HBM bandwidth and β4 multiplies the result, so the documented ~0.27 NVLink-to-HBM ratio is an explanation of β4’s fitted magnitude rather than a factor to divide out. Storing it in Hardware would author a derived value; giving β4 a per-hardware override would make an operator fact hardware-keyed, which is the error #1662 exists to remove. Neither is needed. See R2 task N2.
  3. Layer-group granularity. One group per distinct layer shape is the position in §3. The open part is how fine "distinct" should be for a model whose FFN width varies layer by layer: one group per width, or a width vector inside one group.
  4. Registry release granularity. One release per fit campaign, or per operator? This determines how partial recalibrations compose, and what a leaderboard row cites.
  5. Where the leaderboard store lives. Object storage read by a stateless view, a database for fast cross-release queries, or existing CurveBender results infrastructure. §6 requires only that result artifacts be addressable and immutable.
